# AudiChess friction log

Friction we hit while building AudiChess (Alexa+ track, 15–23 October 2026), in the format the hackathon asks for:
- the task we attempted;
- the steps we took;
- what we expected vs. what actually happened;
- severity;
- the workaround we used;
- an actionable suggestion.

**Severity:**
- **Critical:** it blocked the core experience.
- **High:** it cost hours, or users would notice.
- **Medium:** it needed a non-obvious workaround.
- **Low:** an annoyance.

Every entry comes from something that actually happened in this project: logs from real-mic games, eval harness
runs and deploys.

## 1. Sonic invents user turns and loops on the tool call — Critical

- **Task:** use Nova 2 Sonic as ears and voice only. For every user turn it calls our one tool, `alexa`, and speaks
  the result word for word.
- **Steps:** a system prompt that says to always call the tool with the user's exact words. When the agent had
  nothing to say (background talk), the tool returned an empty string.
- **Expected:** one tool call per thing the user said, and silence when the tool's answer is empty.
- **Actual:**
  - In our eval harness, Sonic called the tool up to 25 times for one utterance after an empty answer.
  - In a real-mic game it made about 75 tool calls in 77 seconds, each with a sentence nobody said: "can you
    explain the rules", "what's the board like", "your move please", "please proceed with your move"…
  - After 8 repeat calls in 3 seconds it stopped hearing the user at all.
- **Workaround:**
  - The page answers each user utterance only once, and every repeat call gets an empty "stay silent" answer.
  - The first repeat call closes the stream and opens a fresh one.
  - The prompt forbids answering from its own knowledge.
- **Suggestion:**
  - Treat an empty tool result as "say nothing" and end the turn.
  - Add a documented setting such as `maxToolCallsPerTurn`.
  - Expose a flag on tool-use events that says whether the call came from a new user transcript or was generated by
    the model.

## 2. No custom vocabulary or biasing for recognition — High

- **Task:** recognise spoken chess moves from an Indian-English speaker.
- **Steps:** listed the chess words in the system prompt ("pawn, knight, bishop, rook… squares like e4"), and
  tested with synthetic and real audio.
- **Expected:** a way to bias recognition toward a small domain vocabulary, like Amazon Transcribe's custom
  vocabulary (which we used before Sonic).
- **Actual:** with a real voice, a reasonable share of moves came back as other words:

  | Said | Heard |
  |---|---|
  | rook g5 | "book g five" |
  | rook d8 | "a jade queen", "eight queen" |
  | e3 | "me three", "only three" |
  | undo the last move | "unbelievable isn't it", three times in a row |
  | knight h4 | "knight h" and "four" as two separate turns |

  Synthetic voices were recognised perfectly, so evals didn't catch any of this.
- **Workaround:**
  - A fuzzy move matcher on our MCP server (sound-alike piece and file words, legal-move scoring).
  - Code that asks "Did you say undo?" for undo-like garbles.
  - Joining split moves across turns.
- **Suggestion:**
  - Add a `customVocabulary` or phrase-boost list to Sonic's session config.
  - Return n-best alternatives (or word confidences) with the user transcript, so apps can re-rank against their
    own grammar.

## 3. The stream goes "deaf" with no error — High

- **Task:** keep one Sonic stream listening for a whole game.
- **Steps:** streamed 16 kHz mic audio continuously and logged the mic level every 10 s.
- **Expected:** a transcript whenever someone speaks, or an error event if the stream stops recognising.
- **Actual:**
  - Several times per game we had 20–40 s stretches with clear speech at the mic (average −25 to −35 dB) and no
    transcript at all, and no error.
  - Only closing and reopening the stream fixed it.
  - Reopening on a timer then cut users off mid-word: "e three" became "me three".
- **Workaround:**
  - A watchdog reopens the stream after 30 s of loud audio with no transcript.
  - It waits for 1.5 s of quiet so it never closes the stream while someone is talking.
- **Suggestion:**
  - Emit a voice-activity or "speech detected" event, so clients can tell "heard nothing" from "ignored speech".
  - Document when Sonic deliberately ignores speech, for example background talk in another language.

## 4. The Indian-English voice writes English in Devanagari — High

- **Task:** offer Indian voices (Kiara, Arjun) to Indian users.
- **Steps:** selected Kiara; the user spoke English.
- **Expected:** English transcripts, since Kiara is listed as an English (India) voice.
- **Actual:** "let's play chess" came back in Devanagari script. A "LANGUAGE LOCK: English only, Latin letters"
  prompt plus Sonic's documented speech prompt only partly helped: with one setting, 2 of 10 more test phrases were
  still in Devanagari.
- **Workaround:** dropped the Indian voices. We now use Amy (British English), plus a page-side filter that drops
  non-Latin transcripts.
- **Suggestion:**
  - Let the session pin the input (ASR) language separately from the output voice, for example
    `inputLanguage: "en-IN"`.
  - Never switch script on a voice that's marketed as English.

## 5. Cognito's enhanced auth flow can never call Bedrock — High

- **Task:** let the static web page call Sonic directly, with guest credentials (no server in the audio path).
- **Steps:** a Cognito identity pool with guest access, a role allowing `bedrock:InvokeModel` and
  `bedrock:InvokeModelWithBidirectionalStream` on the Sonic model, and `fromCognitoIdentityPool` (the enhanced flow).
- **Expected:** guest credentials that can call the actions the role allows.
- **Actual:** access denied. The enhanced flow's built-in session policy doesn't include Bedrock, whatever the role
  says.
- **Workaround:** the classic (basic) flow: get an OpenID token, then call STS `AssumeRoleWithWebIdentity`
  ourselves.
- **Suggestion:**
  - Allow Bedrock runtime actions in the enhanced-flow scope-down policy.
  - Failing that, state the limitation and the classic-flow recipe in the Nova Sonic browser documentation.

## 6. Endpointing is coarse; HIGH answers mid-sentence — Medium

- **Task:** let players finish a sentence ("undo the last move", "bishop… c four") before she answers.
- **Steps:** started with `endpointingSensitivity: "HIGH"` for speed.
- **Expected:** a turn ends after a natural pause.
- **Actual:**
  - The user's feedback was "it hears like 4 words and immediately responds", and moves were split in two.
  - The only control is HIGH / MEDIUM / LOW. LOW added about 1 s (end of speech detected after 1.4 s instead of
    0.3 s) and fixed it, but we can't tune it in between.
- **Workaround:** `LOW`, plus joining split moves in code.
- **Suggestion:**
  - Accept a silence duration in milliseconds.
  - Or allow a per-turn "still talking" hint, so an incomplete utterance ("knight h…") can extend the window.

## 7. Nova 2 Sonic isn't offered in ap-south-1 (Mumbai) — Medium

- **Task:** keep the whole stack in one region, ap-south-1, near our users.
- **Expected:** Sonic available where the rest of our Bedrock usage (Nova 2 Lite) runs.
- **Actual:** Sonic isn't offered in ap-south-1, so the audio stream goes to ap-northeast-1 (Tokyo). That needed a
  cross-region IAM policy and added latency.
- **Workaround:** a separate `SonicRegion` parameter, and IAM scoped to the Tokyo model ARN.
- **Suggestion:**
  - Offer Sonic in ap-south-1.
  - Or offer a cross-region inference profile, like the `global.` profiles for text models.

## 8. No browser-ready way to open Sonic's bidirectional stream — Medium

- **Task:** stream mic audio from the browser straight to Sonic.
- **Steps:** looked for a browser sample, then used `@aws-sdk/client-bedrock-runtime`
  (`InvokeModelWithBidirectionalStreamCommand`).
- **Expected:** a documented browser path, or a small package for it.
- **Actual:**
  - We bundled the SDK for the browser with esbuild ourselves (`scripts/build-sonic-sdk.mjs`).
  - We wrote the event protocol by hand: session start, prompt start, content blocks, audio input, tool results.
    Its exact order rules are spread across the documentation.
- **Workaround:** our own `web/sonic.js` session wrapper (about 250 lines), with 30 unit checks for event order.
- **Suggestion:**
  - Publish an official browser sample (Cognito guest + Sonic + mic worklet).
  - Publish a typed event-builder helper for the bidirectional protocol.

## 9. The content filter blocked a harmless sentence — Medium

- **Task:** have Sonic speak our tool's text word for word.
- **Actual:** "Alright, I'm easy level…" (meaning the chess difficulty) tripped Sonic's output filter. The reply
  wasn't spoken.
- **Workaround:** the agent says "easy level", never "I'm easy".
- **Suggestion:**
  - Return a structured `contentFiltered` event with the category, so apps can rephrase.
  - Allow a less strict mode for text the app supplies through a tool result.

## 10. A throttled background tab closes the stream — Medium

- **Task:** keep listening while the user switches tabs.
- **Actual:** the stream closed with "Audio bytes were being streamed too slowly. Please stream audio in realtime."
  Most likely the browser throttled the page's audio while it was in the background.
- **Workaround:** reconnect with backoff, and pause listening after 5 minutes of silence.
- **Suggestion:** tolerate short audio gaps, or let the client send an explicit "pause audio" event instead of
  silence frames.

## 11. Nova 2 Lite refuses chess help, leaks reasoning, copies examples — Medium

- **Task:** answer 305 kinds of chess questions for a blind player, as their opponent.
- **Actual:**
  - Refusals: "that would be cheating", "a strategic advantage I can't give away". The skill says that answering
    is never cheating.
  - Once, a 170-word reasoning monologue was spoken aloud without `<thinking>` tags.
  - Few-shot banter examples were copied word for word ("Flattery won't save your king, though" twice).
- **Workaround:**
  - Code answers for the most refused questions.
  - One retry when a chess question is refused.
  - A reasoning-leak filter.
  - Examples marked "spirit only".
- **Suggestion:**
  - A documented way to declare a "game opponent that also assists" persona.
  - A guarantee that reasoning never appears outside the reasoning channel.

## 12. Nova 2 Lite calls analysis tools for small talk — Medium

- **Task:** a rival that never coaches unless asked.
- **Actual:** "that's an interesting move" made the model call `analyze_position` and announce "the best move here
  would be pawn to d4". A misheard "eight queen" got "You have a forced mate in one".
- **Workaround:** before the model sees analysis nobody asked for, the agent strips best moves, threats and mate
  counts.
- **Suggestion:** a per-tool "call only when the user asks" hint in Converse `toolConfig`, honoured by the model.

## 13. Model IDs and IAM in ap-south-1 — Medium

- **Task:** call Nova models from Lambda in ap-south-1.
- **Actual:**
  - On-demand calls with the plain model ID `amazon.nova-pro-v1:0` were rejected; an inference profile
    (`apac.` / `global.`) was required.
  - IAM then needed wildcard regions (`arn:aws:bedrock:*::foundation-model/*`), because the profile routes across
    regions.
- **Workaround:** use `global.amazon.nova-2-lite-v1:0`, with wildcard-region IAM.
- **Suggestion:**
  - When the plain ID is rejected, name the inference profile to use in the error message.
  - Provide a managed policy for "invoke this profile wherever it routes".

## 14. No path to a real Alexa+ device — Medium

- **Task:** the track: an MCP integration for an Alexa+ experience.
- **Expected:** a way to register our Streamable HTTP MCP server with Alexa+ and try it on an Echo.
- **Actual:**
  - We didn't find a developer path to connect a custom MCP server to a real Alexa+ during the hackathon.
  - The track allows a simulation, so we built an Echo-style web page with Nova 2 Sonic standing in for the device.
  - We can't confirm how the server would behave with Alexa+'s own speech and turn-taking.
- **Workaround:** the web simulator. The MCP server is standard: stateless Streamable HTTP with bearer auth, and the
  official MCP client and Inspector both work with it.
- **Suggestion:** open an Alexa+ developer preview for custom MCP servers, even if it's limited to the developer's own
  device.

## 15. Small Sonic gaps — Low

- **8-minute session limit.** We renew the stream between turns after 7 minutes. A documented "resume session"
  call would keep the context.
- **No speaking rate.** The voice speed can't be changed. For blind players, who hear every read-out, a
  `speechRate` setting would help accessibility.
- **Hyphenated squares.** Transcripts write squares as "e-four", which our filters took for non-chess words. We now
  normalise them. Documenting how digits and letters are formatted in transcripts would help.

## 16. Streamable HTTP on Lambda needed an adapter — Low

- **Task:** host the MCP server on AWS Lambda behind a function URL.
- **Actual:**
  - The spec allows stateless JSON mode (no `MCP-Session-Id`, GET returns 405), and it fits Lambda well.
  - We still had to write the Lambda ⇄ web-request adapter ourselves.
  - We added `Origin` checks and bearer auth by hand.
- **What worked well:** once running, the official MCP client and MCP Inspector connected with no changes.
- **Suggestion:** an official Lambda handler for the MCP TypeScript SDK (stateless mode, auth hook, Origin
  allowlist).
